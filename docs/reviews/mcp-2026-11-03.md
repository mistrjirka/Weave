# MCP capability review · 2026-11-03

## Coverage

Compared the OpenAPI routes with MCP operation discovery and checked the request/response formats, authorization, side effects and response bounds. A Luna subagent independently reviewed the gaps; the implementation was checked against the findings and the official MCP specification.

The existing discovery/description/call pattern covers project CRUD, graph validation/code generation, stages and scripts, launch overrides, run control, checkpoints, validation settings, hardware tuning and checkpoint chat/tests. It avoids maintaining a second implementation of those operations. Agents must inspect an operation's schema before calling it; MCP annotations describe behavior but do not grant authorization.

## Gaps corrected

| Finding | Correction |
| --- | --- |
| Multipart tokenizer/dataset/snapshot imports were absent from the JSON bridge. | `upload_weave_files` accepts bounded caller-supplied bytes and delegates to the existing multipart API. Tokenizers retain companion configuration/chat-template files. It cannot read an arbitrary server path. |
| Model/training ZIPs and run artifacts were excluded because they are binary/text responses. | `download_weave_file` returns bounded embedded resources with filename, byte count and SHA256. Text artifacts remain confined to the named run; checkpoint weights use HTTP. |
| Transcript export advertises JSON in OpenAPI but returns NDJSON. | The read adapter parses NDJSON into records; the file adapter can return the original transcript. |
| Long histories could exceed the JSON response cap, and the normal run detail includes logs and other large fields. | Authenticated `/status` returns a small progress summary; `/event-records` provides chronological, record/byte-bounded pages with a continuation cursor. Neither changes the UI's existing endpoints. |
| Every GET was classified as read-only, including the endpoint that probes a caller-selected Python executable. | Environment probing requires the execution tool. Listed pure graph-calculation POSTs can use the read tool with a request body. |
| HTTP permission/validation failures looked like successful MCP calls containing error text. | Operation/file adapters return MCP error results and preserve HTTP status/details. Existing JSON text content is retained alongside structured content. |
| Documentation was accessible only through custom tools; client configuration was underspecified. | Added documentation resources, a graph-design prompt, and copyable JSON/HTTP/stdio Codex configuration examples. Historical guide IDs remain valid. |

## Deliberate limits

- Files are capped at 4 MiB per call; generic JSON responses at 1 MB. This supports scripts, small catalogs/datasets and model source exports without pretending to transfer multi-gigabyte training artifacts through a model context. Large files use the normal HTTP API/UI.
- Export URIs identify embedded response contents; they are not persistent `resources/read` handles. Packaging may create a derived ZIP cache through the existing API.
- SSE and scoped script-report ingestion remain separate transports. Agents poll JSON status/events; training scripts use their reporting API.
- The server's login/session endpoint is not exposed as an agent tool. HTTP callers supply their own credential; a stdio client may explicitly forward its environment credential. The HTTP bridge cannot borrow the server's training secret.
- Viewport position, browser undo and unsaved local UI drafts are not server-domain operations. Saved graph documents are editable.
- The execution tool covers heterogeneous operations and is conservatively marked potentially destructive. The API continues to enforce credentials, containment and validation; annotations are hints for clients.

## Verification

Regression tests cover read/execution classification, pure POST calculations, MCP error results, caller authentication, cursor ordering and byte limits, NDJSON transcripts, tokenizer companion files, invalid uploads, model/training exports, snapshot import, traversal rejection, documentation resources/prompts and configuration parsing. Existing HTTP transport/authentication and documentation/export checks also run.

The setup examples use real CLI-supported fields. The Codex configuration was checked with `codex mcp get` using command-line overrides, without changing the user's stored configuration.

All 28 backend regression checks passed. Real MCP clients connected over HTTP and stdio, read resources/prompts, called health and verified that environment probes are rejected by the read tool. Stdio was launched from outside the checkout using the documented `PYTHONPATH` setup. A fresh Docker training image passed the same transport checks and completed two optimizer updates; the new status endpoint and paginated event records exposed its progress and metrics.
